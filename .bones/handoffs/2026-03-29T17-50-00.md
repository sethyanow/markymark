## Context for Next Session

### BLOCKER: OpenSSL on Linux release builds (unsolved)

`fastembed` depends on `native-tls` (via `hf-hub-native-tls` and `ort-download-binaries`), which depends on `openssl-sys` on Linux. The Bazel hermetic LLVM toolchain uses `--sysroot=/dev/null -nostdlibinc` — this blocks ALL system headers including OpenSSL, even with `OPENSSL_DIR` set. The vendored approach also fails because the vendored OpenSSL C build needs the same system headers the sysroot blocks.

**Approaches tried and failed:**
1. `--action_env=OPENSSL_DIR=/usr` — hermetic clang can't access `/usr/include` through sysroot
2. `apt-get install libssl-dev` — same sysroot issue
3. `openssl = { features = ["vendored"] }` in workspace — vendored OpenSSL build also blocked by sysroot; broke Windows build
4. `cfg(unix)` target-specific dep — still blocked by sysroot on Linux

**Approaches NOT yet tried:**
1. Switch `fastembed` from `hf-hub-native-tls` to `hf-hub-rustls-tls` — eliminates OpenSSL dep on hf-hub side. But `ort-download-binaries` still forces `ort/tls-native`.
2. Replace `ort-download-binaries` with separate `ort/download-binaries` + `ort/tls-rustls` — would require forking or patching fastembed's feature definitions.
3. Bazel-managed OpenSSL external dependency with proper sysroot integration.
4. Relaxing `toolchains_llvm_bootstrapped` sysroot to include `/usr/include` for specific actions.

**What works:** macOS (4/4 runs passed) and Windows (passes when not poisoned by vendored OpenSSL).
